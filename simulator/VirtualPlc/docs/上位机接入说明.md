# 上位机接入虚拟 PLC

## 1. 接入边界

上位机通过 Modbus TCP 控制运动和读取设备反馈；相机、扫码和算法不经过 PLC。虚拟 PLC/真实 PLC 的角色是 Modbus TCP Slave/Server，上位机的角色是 Master/Client。虚拟 PLC 与真实 PLC 应实现同一份点表，上位机业务层只依赖一个 PLC 接口。

建议上位机结构：

```text
Workflow / Motion Coordinator
              |
          IPlcClient
          /        \
 ModbusPlcClient   其他真实 SDK 适配器（如果最终不用 Modbus）
        |
  虚拟 PLC 或真实 PLC
```

如果真实 PLC 最终也使用 Modbus TCP，通常只需修改 IP、端口和 Unit Id，不需要再写第二套业务流程。

## 2. 轮询建议

- 按规范每 50ms 左右读取一次状态块。
- 每次读取后，将 `PLC_Heartbeat_Req` 当前值写入 `PC_Heartbeat_Resp`。
- 连续 3 秒没有有效心跳，按通信故障处理，停止下发新动作并等待人工复位。
- 状态轮询不要直接推进复杂业务；先形成 PLC 状态快照，再由流程状态机判断下一步。

## 3. 动作统一模式

每个动作按以下方式处理：

1. 写参数，例如坐标、槽位号。
2. 把命令寄存器写 0，确保为新命令做准备。
3. 写非 0 命令值。
4. 等待“执行中/完成/失败”状态。
5. 完成后把命令恢复 0。

上位机不能把 Modbus 写成功当成设备动作完成。对应状态返回到位/成功时走正常路径；等待超时时按第 5 节记录错误并继续模拟路径。

## 4. 推荐接口语义

上位机可以先定义这些业务方法：

```csharp
public interface IPlcClient
{
    Task ConnectAsync(CancellationToken cancellationToken);
    Task<PlcSnapshot> ReadSnapshotAsync(CancellationToken cancellationToken);
    Task MoveAsync(ushort targetX, ushort targetY, ushort targetZ,
        ushort moveCode, CancellationToken cancellationToken);
    Task FlipAsync(ushort flipCode, CancellationToken cancellationToken);
    Task SortAsync(ushort partIndex, CancellationToken cancellationToken);
    Task SetPalletLockAsync(bool locked, CancellationToken cancellationToken);
    Task ConfigureZonesAsync(ushort ngCount, ushort pendingCount,
        CancellationToken cancellationToken);
}
```

`MoveAsync` 返回正常成功应代表 XY 和 Z 均已到位。模拟模式必须区分“等待超时”和“明确失败”：明确失败交给流程状态机阻断；等待超时返回或抛出可识别的超时结果，由上位机记录错误后继续下一步。相机或算法异常不应伪装成 PLC 异常。

## 5. 本轮流程错误策略

### 阻断并报警

- PLC 通信中断或心跳超时。
- PLC_System_Fault 为 1，包括 PLC 已明确判定的 XY/Z 故障。
- Manual_Zone_Occupied 为 1。
- `Flip_Status=3`、`Sorting_Exec_Status=3/4` 或 `Pallet_Lock_Status=2`。
- 翻转角度与本次命令不一致。

### 记录后继续模拟流程

- 相机采集、扫码、算法、配方、数据保存、MES 等上位机步骤失败。
- 普通检测结果缺失或其他非 PLC/下位机故障。
- XY/Z 或翻面动作超过上位机设定的等待时间：等待结束后记录超时错误，继续下一步模拟流程。
- `XY_Pos_Confirmed=2` 按运动超时处理，记录错误后继续模拟流程。
- `Z_Axis_Move_Status=3` 且 `PLC_System_Fault=0` 时，当前模拟策略按超时处理，记录错误后继续；若同时有 PLC 故障信号，则按明确失败阻断。

模拟模式下统一应用“阻断白名单”：PLC 通信故障、安全报警、明确的下位机动作失败和翻转角度不一致阻断；XY/Z 和翻面等待超时只记录错误并继续。需要判定结果时生成随机 OK/NG/Pending，不需要判定结果时生成模拟成功反馈。这样可以继续验证翻面、分拣、归档和界面完整流程。生产模式必须关闭这个策略。

调用模拟器的流程辅助接口时，XY/Z 或翻面等待超时使用 `category=DeviceTimeout`。返回结果为 `continueFlow=true`、`shouldReportError=true`，表示上位机既要记录错误，也要继续模拟流程。明确动作失败和翻转角度不一致仍使用 `category=DeviceAction`，返回阻断。

建议配置：

```json
{
  "RunMode": "Simulation",
  "NonDeviceFailurePolicy": "ContinueWithFallback",
  "StopOnDeviceFault": true,
  "ContinueOnDeviceTimeout": true
}
```

## 6. 真实 PLC 切换前必须再次确认

- Modbus 客户端库采用零基还是一基地址。
- X/Y/Z 的单位、正负数和缩放倍数。
- 命令清零责任、重复命令处理和动作超时时间。
- `Z_Axis_Move_Status=3` 在 V6.0 中同时表示“超时/失败”，无法满足“超时继续、明确失败阻断”的区分要求；正式点表应拆分状态值或增加故障原因寄存器。在拆分前，上位机自身等待计时器到期按超时继续，PLC 同时置位 `PLC_System_Fault` 时按明确故障阻断。
- 故障码实际地址。现有规范描述了故障码，但没有在点表中分配寄存器。
- PLC 断电后状态、编码器位置和恢复操作。

## 7. 变更记录

### 2026-09-16

- 主程序和冒烟测试目标框架由 `net8.0` 升级为 `net10.0`，并增加 .NET 10 SDK 选择文件。
- 明确通信角色：虚拟 PLC/真实 PLC 为 Modbus TCP Slave/Server，上位机为 Master/Client。
- 完成 V6.0 点表核对：8 个线圈、21 个保持寄存器，共 29 个信号的地址、名称和方向一致。
- 增加区域配置互锁：`Zone_Config_Ack=1` 前不允许启动运动、翻面和分拣。
- 增加软停处理：运行中收到 `Soft_Stop_Cmd=1` 时立即终止当前模拟动作并反馈失败状态。
- 增加分拣索引校验：`Sorting_Cmd=1` 时 `Sorting_Part_Index` 不得为 0。
- 调整模拟错误策略：XY/Z 和翻面等待超时改为“记录错误后继续”；明确动作失败仍阻断。
- 保留翻转角度校验：`Flip_Result_Angle` 与本次命令不一致时继续阻断并报警。
- 记录 V6.0 接口缺口：故障码无寄存器、动态区域满盘缺少目标区域/占用量、实际槽位无反馈、坐标编码未定义、Z 轴状态无法区分超时和失败。
