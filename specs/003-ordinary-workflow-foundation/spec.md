# Feature Specification: 普通整盘中台流程框架

**Feature Branch**: `003-ordinary-workflow-foundation`
**Created**: 2026-09-17
**Status**: Implemented — Application框架；见validation.md
**Input**: 用户要求继续搭建框架；以V1.3、普通整盘路线及上一增量验证为依据，先做不依赖下位机点表的中台Application层。

## User Scenarios & Testing

### User Story 1 - 公共准备和冻结计划 (Priority: P1)

中台开发者可从设备就绪开始一次测试盘任务：先获得首轮定位结果，再读取F托盘码，以托盘码加场景唯一匹配方案，固定零件身份和方案版本。

**Why this priority**: 防止无身份、无可靠坐标就下发后续动作。
**Independent Test**: 使用记录请求顺序的假设备，验证成功准备及定位/扫码/方案缺失或歧义时停止。

**Acceptance Scenarios**:
1. **Given** 设备就绪且首轮定位返回两个槽位，**When** F读到托盘码并唯一匹配方案，**Then** 方案与两个PartId固定，首面使用第一批坐标。
2. **Given** F读码失败或匹配0个/多个方案，**When** 处理结果，**Then** 准备失败，后续检测动作数为0。
3. **Given** 定位失败，**When** 处理结果，**Then** 不请求F扫码或依赖坐标的运动。

### User Story 2 - 单运动通道和整盘分面顺序 (Priority: P1)

中台开发者可为两个零件按面、相机组顺序发起采集；跨面前先逐件翻面，重做3D定位，拒绝上一批坐标。

**Why this priority**: 这是将当前只读计划转成可执行任务的最小业务骨架。
**Independent Test**: 确认面1 A1/A2/B1/B2，再两次翻面、再3D，再面2 A1/A2/B1/B2；每时刻至多一个运动请求。

**Acceptance Scenarios**:
1. **Given** 已准备的两件两面方案，**When** 逐一送达当前动作/采集完成事件，**Then** 顺序准确且共8次计划采集。
2. **Given** 上一动作的迟到完成或仅有受理，**When** 当前动作仍待完成，**Then** 不推进下一动作。
3. **Given** 动作结果未知，**When** 中台收到该结果，**Then** 停止新增动作，保持对账状态，不自动重发。
4. **Given** 翻面完成，**When** 尚未收到新3D定位，**Then** 下一面不能沿用旧坐标。

### User Story 3 - 采集与算法技术终态 (Priority: P2)

中台开发者可独立收到采集与算法结果；普通检测帧缺失保留失败事实并继续安全的其他采集，算法结果乱序也能关联正确工件。

**Why this priority**: 为后续判定和保存提供完整的技术事实。
**Independent Test**: 混合成功、缺帧、算法失败、迟到与截止事件，检查所有计划输入形成终态且不串件。

**Acceptance Scenarios**:
1. **Given** 一张普通检测图未取得，**When** 采集失败返回，**Then** 该项记录失败，后继算法标依赖失败，安全前提仍成立时继续下一采集。
2. **Given** 算法结果乱序或重复，**When** 对应事件到达，**Then** 只当前有效任务改变一次；旧结果不覆盖。
3. **Given** 全部运动/采集已收敛且仍有算法在运行，**When** 截止到达，**Then** 未完成算法记超时，输出“待判定”事实，不自动形成OK/NG或放行。

### Edge Cases

- 初始定位槽位重复、空、与计划不符；翻面后3D找不到原工件或出现额外工件。
- 完成早于受理、上一动作/上一坐标批次反馈、重复完成、取消后的迟到事件。
- 采集返回错误件/面/相机/尝试，或同一帧重复；算法返回旧尝试结果。
- 运动通道满、执行未知、设备明确失败，均不能隐式放行。

## Requirements

### Functional Requirements

- **FR-001**: 系统必须按“设备就绪→初始3D→F托盘码→场景匹配唯一方案”组织公共准备；失败阻止依赖动作。
- **FR-002**: 系统必须保持固定TrayRunId、PartId、方案版本，翻面只更新坐标批次。
- **FR-003**: 系统必须按面、相机、件的顺序发出运动/采集请求，翻面后重扫才允许下一面。
- **FR-004**: 系统必须一次只接受一个整体运动；按当前请求标识处理受理、完成、失败与未知，迟到结果不得推进。
- **FR-005**: 系统必须以身份、面、相机、尝试关联帧和算法结果，并形成成功、失败、依赖失败或超时终态。
- **FR-006**: 普通检测图缺失必须记录后继续安全的独立采集；身份、定位或运动状态未知则停止受影响动作。
- **FR-007**: 本增量产出技术事实与“待判定”状态，不把未保存/未判定的盘标为业务完成或允许放行。
- **FR-008**: 正式设备通信与扫码/3D/相机/算法接入通过独立端口，测试替身不能冒充已接入实际设备。

### Key Entities

- TrayRun：当前盘身份、场景、托盘码、冻结方案、阶段。
- Part：稳定PartId与槽位；翻面后仍为同一PartId。
- CoordinateSnapshot：当前定位批次及各件有效坐标；新批次使旧坐标失效。
- MotionOperation：动作标识、件、面、坐标批次、受理/完成/失败/未知。
- CaptureSet/AlgorithmTask：件/面/相机/尝试、输入引用、技术终态。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 两件两面AB样例产生恰好8个按预期顺序的采集请求、2个逐件翻面请求和2轮定位请求。
- **SC-002**: 关键准备失败、运动未知、过期反馈、旧坐标四类反例均阻断不安全推进。
- **SC-003**: 所有安全可执行采集结束且算法截止后，全部8项都有明确技术状态，零项被默认为成功。
- **SC-004**: 不调用实际设备的框架测试可重复执行且行为一致；未完成的质量/保存/分拣不显示为已验收。

## Assumptions

本轮仅实现进程内业务框架与接口级测试；不提供生产启动入口或断电恢复证明。普通检测缺帧继续的前提是设备/身份/坐标仍可信。3D和F扫码结果来自各自端口，不由PLC随机业务辅助接口生成。跨进程设备编码、真实单位和物理互锁由后续已确认协议实现。
