# Feature Specification: V1.3 整体软件框架

**Feature Branch**: `framework-v13-foundation`
**Created**: 2026-09-17
**Status**: Draft
**Input**: 用户要求先按 V1.3 搭整体框架，不在框架 PR 实现具体工位；以后每个工位分阶段实现、测试、修正、提交 PR，并执行架构书第 18 节测试。

## User Scenarios & Testing

### User Story 1 - 团队看到同一套模块与能力边界 (Priority: P1)

中台、前端、下位机和算法同学可从版本化合同看见 V1.3 的五层、十五个责任模块、各模块所有者及当前交付状态。运行中的 Host 给出同一架构版本、未实现能力与生产就绪状态；不存在“空实现返回成功”。

**Independent Test**: 查询已发布 Host 的系统状态，与模块表逐项核对 15 个唯一责任模块、当前未交付能力和 `productionReady=false`。

**Acceptance Scenarios**:
1. **Given** 只有本框架增量，**When** 前端读取系统状态，**Then** 获得 V1.3、完整模块清单、明确的未实现能力及非生产状态。
2. **Given** 调用尚未实施的任务命令，**When** Host 处理请求，**Then** 返回稳定、可机器识别的未实现错误，不生成任务、不发送设备动作。
3. **Given** 旧协议工程探针与内存流程仍存在，**When** 查看能力状态，**Then** 二者分别标明工程/框架用途，不显示为 V1.3 工位完成。
4. **Given** 前端打开最小状态页，**When** Host 可达或不可达，**Then** 页面分别显示真实的非生产模块状态或连接错误，不提供虚假的启动/急停控件。

### User Story 2 - 后续工位按同一入口逐步接入 (Priority: P1)

开发者能按明确的项目依赖和端口归属增加 S01、F、A/B/C/D、E 等工位能力。每个工位在其 PR 内补具体适配、状态迁移、错误处理和测试；不会复制新的 Host 或另一套业务流程。

**Independent Test**: 静态检查项目依赖与组合根；现有测试全部通过；框架中不包含新增具体工位动作或真实设备参数。

**Acceptance Scenarios**:
1. **Given** 未来工位功能，**When** 准备实现，**Then** 文档可定位 Application 端口、Infrastructure 适配、Host 装配、外部合同和相应验收层。
2. **Given** 正式 PLC、相机、算法或数据库未绑定，**When** Host 启动，**Then** 可提供健康/状态查询，但不会自动装配合成成功设备或启动生产任务。

### User Story 3 - 每阶段测试与 PR 结论可核查 (Priority: P2)

评审者能按 V1.3 第 18 节核对框架、单工位、全虚拟、真实算法、混合联调与整机验收的测试证据；未运行项保持未运行。

**Independent Test**: 检查映射表含架构书必测场景和数据库维护场景，逐项标明责任阶段、测试层、证据与当前状态；框架 PR 只执行适用的骨架检查。

**Acceptance Scenarios**:
1. **Given** 框架 PR，**When** 审阅测试报告，**Then** 可区分当前编译/HTTP/旧协议回归与尚未运行的 V1.3 工位、完整整盘及真机测试。
2. **Given** 一个工位 PR，**When** 准备合并，**Then** 必须有本工位正常/故障、跨端口、独立设备轨迹及影响回归的实际结果；失败先修正并复测。

### Edge Cases

- 旧系统状态字段被新模块字段替换，导致现有前端或测试读不到；新字段应向后兼容。
- 缺少真实适配器时误把合成源装入生产模式，或把 Accepted 当 Completed。
- 某模块只有接口或测试替身，却被标为生产可用。
- 新增模块状态与文档/Spec Kit 任务不一致；不以模块目录存在或 PR CI 绿色证明业务通过。
- 系统状态可查询不等于所有设备 Ready；本框架不声明 WPF、Python 或数据库部署已完成。

## Requirements

### Functional Requirements

- **FR-001**: 必须有一份 V1.3 五层/十五责任模块的唯一映射，说明职责、代码位置、所有者、当前状态与未来接入点；不强制拆为十五个项目/进程。
- **FR-002**: 必须保留唯一正式 Host 与 Domain → Application → Infrastructure/Host 的依赖方向；外部接口 DTO 与业务状态机职责分离。
- **FR-003**: Host 必须提供架构版本、模块状态、未实现能力、运行模式和 `productionReady` 的只读状态；默认运行模式不触发硬件或模拟动作，已有状态字段保持兼容。
- **FR-004**: 对尚无实现的生产命令，Host 必须明确拒绝并返回稳定错误码；不得以成功回执、默认配方、随机设备反馈或模拟到位替代。
- **FR-005**: 必须记录全模拟、图像回放、混合联调、人工交接与生产的来源/切换边界；本增量只定义合同，不接具体设备。
- **FR-006**: 必须把 V1.3 §18 的架构/流程/设备/数据/算法/界面/恢复及数据库部署验收映射到后续增量；每个工位 PR 具有明确测试、修正、PR 和合并后回归门槛。
- **FR-007**: 现有普通整盘内存流程、旧 V6 真实 Modbus 联调及工程探针应保持可构建和可回归，但不得显示为新 V1.3 工位或完整整盘已交付。
- **FR-008**: 不在此框架 PR 实现 3D/F/A/B/C/D/E 工位、真实配方、Python 算法、质量判定、分拣或数据库迁移行为；其业务输入/输出随各自工位或横向能力 PR 冻结。
- **FR-009**: 必须提供一个离线可构建的最小 Vue/TypeScript/Pinia 状态页，只从 Host 读取系统状态；连接失败显示错误，未实现能力不呈现可执行控件。

### Key Entities

- **ModuleDescriptor**: 唯一模块 ID、V1.3 层、职责、所有者、当前交付状态。
- **CapabilityDescriptor**: 具体可运行能力、适用模式、证据等级和未就绪原因；模块存在不等于能力可用。
- **SystemStatus**: 架构版本、阶段、运行模式、生产就绪、模块与不可用能力快照。
- **OperationProblem**: 稳定错误码、中文摘要、关联 ID 与不可执行原因；不承诺本阶段业务命令成功。
- **AcceptanceCase**: 架构书场景、责任阶段、测试层、预期、运行证据和状态。

## Success Criteria

- **SC-001**: 十五责任模块均有唯一映射，运行状态返回同样十五个模块，无缺项/重复项。
- **SC-002**: 已发布 Host 的未实现命令返回明确非成功状态和稳定错误码，整个框架测试期间设备动作数为零。
- **SC-003**: Linux/Windows 锁定依赖构建、现有核心/旧协议回归及新增架构合同检查通过；报告单列未运行层。
- **SC-004**: V1.3 §18 每组必测场景都能在测试映射中定位责任阶段和证据要求；首工位 Draft PR 明确依赖框架 PR。
- **SC-005**: 最小 UI 在 Linux/Windows 可重复安装、类型检查、构建与组件测试；页面从 Host 响应显示 15 模块和非生产状态，离线构建不依赖 CDN。

## Assumptions

沿用现有四个后端项目和唯一 Host，必要时增加稳定外部合同项目；不为空职责建空程序集。前端原型仍作为视觉/页面依据，本增量只做最小只读状态页，不实现完整界面或 WPF；Python 算法与生产数据库/配方未接入。正式点表、SDK、采集参数与工艺阈值由后续负责人确认；框架只定义接入边界与未就绪状态。
