# Feature Specification: 开发基础与普通整盘采集计划预览

**Feature Branch**: `main`（空仓库的首个工程基线）

**Created**: 2026-09-15

**Status**: Implemented — engineering foundation only; see validation.md

**Input**: 用户要求以 yyh V1.3 使用 Spec Kit 开始开发，在 Linux 开发、Windows 部署、GitHub 测试。
首版演示先普通零件整盘多面全虚拟闭环，随后真实算法与特殊零件。

本特性是首版闭环的基础增量：建立可运行、可测试的工程及只读采集计划预览。
完整闭环包含执行、图像、算法、保存、分拣与恢复，另见 `docs/ordinary-tray-roadmap.md`。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 三位开发者共享可验证的工程基线 (Priority: P1)

开发者获取仓库后可以按说明启动后端、执行基础检查，知道各自负责什么和使用哪份架构。

**Why this priority**: 防止三人分别开发出不兼容的业务流程与环境。

**Independent Test**: 从新检出目录执行说明中的构建、测试、启动操作，查询服务存活信息。

**Acceptance Scenarios**:

1. **Given** 核心开发环境已就绪，**When** 运行基础检查，**Then** 完成构建、规则和接口测试。
2. **Given** 无任何设备、模型或业务数据库，**When** 启动后端，**Then** 可以查询存活状态，生产就绪必须为否。
3. **Given** 新提交，**When** 两种平台的自动检查执行，**Then** 各自保留成功或失败结果，不能把未执行项记为通过。

### User Story 2 - 查看普通零件整盘多面采集顺序 (Priority: P1)

开发者查看一个明确标为测试样例的计划，用于后续界面和流程实现对照。

**Why this priority**: 首先把“按面、相机、零件批采”的核心业务规则做成可检查结果。

**Independent Test**: 输入不同零件和检测面组合，检查每次采集顺序、翻面/重扫屏障和原零件身份。

**Acceptance Scenarios**:

1. **Given** 2 个零件、2 个面、每面 A/B 各一次，**When** 生成计划，**Then** 共 8 次采集，
   每面顺序为 A-零件1、A-零件2、B-零件1、B-零件2。
2. **Given** 第一个面采集计划结束，**When** 进入第二面计划，**Then** 明确标出翻面后必须整盘重扫的屏障，
   零件身份不变，计划不携带旧坐标供下一面直接使用。
3. **Given** 选择 C/D 或增加零件/检测面，**When** 重新生成计划，**Then** 保持相机优先的整盘顺序。
4. **Given** 空配置、重复或空零件/面标识、未定义相机组，**When** 生成计划，**Then** 明确拒绝无效输入。

### User Story 3 - 按共同契约准备虚拟下位机对接 (Priority: P2)

用户能把接口草案及测试矩阵交给虚拟下位机同学评审，了解哪些已确认、哪些必须共同冻结。

**Why this priority**: 对接尚未定稿，先统一动作语义与故障行为可减少反复修改。

**Independent Test**: 文档逐条对应 V1.3 的命令关联、超时、重连、故障注入与验收要求。

**Acceptance Scenarios**:

1. **Given** 同学还未确认协议，**When** 阅读草案，**Then** 能区分建议字段、待定编码和已有架构约束。
2. **Given** 丢失完成反馈或虚拟设备重启，**When** 检查验收矩阵，**Then** 存在禁止重复物理执行及未知状态恢复用例。

### Edge Cases

- 存活查询成功不能表示设备、模型或数据库已经生产就绪。
- 计划预览不能下发运动命令，不能生成虚假的执行完成、质量结果或追溯记录。
- 第一个面需要公共准备扫描；后续面需要完成翻面并重扫。屏障是流程要求，不代表已执行。
- 调用者在生成后修改输入集合不能改变已生成计划。
- 同一个零件跨面保持身份；槽位变化及实际定位由后续运行流程处理。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 保存 V1.3 原文基准、来源校验值、三人分工与已确认决策。
- **FR-002**: 提供可重复的工程构建、测试、启动说明与两平台自动检查。
- **FR-003**: 提供只读存活与工程状态查询，明确生产尚未就绪。
- **FR-004**: 按输入的面顺序、相机组顺序、零件顺序生成不可被输入修改的采集计划。
- **FR-005**: 每面必须声明扫描要求；第二面起声明翻面屏障，保留零件身份且不复制坐标。
- **FR-006**: 拒绝空、重复标识及未定义相机组；支持 A/B、C/D 与可替换数量。
- **FR-007**: 提供测试样例计划查询，明确仅预览、不执行和不是生产检测方案。
- **FR-008**: 提供待共同确认的虚拟设备契约及分层测试矩阵，涵盖 V1.3 数据库维护。

### Key Entities *(include if feature involves data)*

- **零件标识**：同一次托盘任务内的稳定身份，不是可随翻面变化的槽位。
- **检测面配置**：面标识及选用相机组，顺序由检测方案给定。
- **每面采集计划**：翻面/扫描前置要求和按相机分批的有序采集条目。
- **工程状态**：运行程序及基准版本、当前能力、生产未就绪原因。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全新环境按文档完成核心构建、测试、启动与查询，两平台分别有自动检查记录。
- **SC-002**: 用户确认样例恰好输出 8 次采集、2 个扫描屏障和 1 个翻面屏障，顺序与身份正确。
- **SC-003**: 无效输入全部被拒绝；计划生成后不受调用者修改输入影响。
- **SC-004**: 接口文档逐项标明冻结状态，测试矩阵明确基础检查与完整闭环、协议、桌面、真机验收的区别。

## Assumptions

- 本增量不实现设备动作、图像接管、算法执行、业务库或 WPF；不宣称完整闭环已完成。
- 首样例按用户 2026-09-15 确认，后续可替换，不产生生产阈值或相机参数。
- GitHub 托管 runner 先运行核心检查；现有 Windows 服务器后续接入实际部署、桌面与 SDK 联调。
- 生产协议编码待双方确认，不影响纯计划规则与基础工程实现。
