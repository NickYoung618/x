首个可替换测试样例是 **2 个零件、2 个面、每面 A/B 各一张，共 8 次检测采集**；
3D 扫描、F/E 扫码不计入这 8 次，也不是生产型号或正式检测方案。

准备顺序：工单/检测场景 → PLC 实体就绪和夹紧 → 初始 3D → F 相机读取托盘码 →
根据“托盘码 + 场景”匹配唯一检测方案并冻结版本 → 第一面 A 全盘、B 全盘 →
整盘完成一轮翻面 → 重新 3D 定位 → 下一面 A/B → 终态、判定、分拣、必要保存和放行。
E 相机后来读取**零件码**，绑定已经存在的 PartId；不能拿 E 扫码代替 F 扫码选方案。
第一次 3D/F 使用公共准备流程，不能依赖扫码后才知道的检测方案。

### 接入前需要正面处理的差异

1. 同学依据 2026-09-08 的旧 V6.0 资料；本地还有 2026-09-11 的
   `/home/ubuntu/dzk/gaode/文档/PLC与上位机通信接口协议.docx`。
   坐标一个是单寄存器 16 位，一个是 Float32 两寄存器；V1.3 还要求明确单位、符号、字序等。
   需要共同确认一份**版本化接入点表**，不能只看信号名称相同。
2. 旧模拟器用“0→非0”触发动作，缺会话/命令序号及受理/完成关联。
   V1.3 要求旧反馈不推进新动作；若暂用兼容握手，断线后必须对账，不能盲目重发翻面或分拣。
3. 旧 `/api/simulator/flow-decision` 在扫码、方案、保存失败时生成随机 OK/NG/Pending 并继续，
   动作超时也继续。本轮调用实际确认；这些规则与 V1.3 冲突，不能交给正式 Workflow 使用。
4. 分拣参数/去向/占用和独立动作轨迹不足以核查完整取放位置与实际执行次数。
5. 虚拟 PLC 不提供 F 托盘码、3D、相机帧和算法输入。中台还需独立的模拟适配。
6. 同学原验证入口依赖 .NET 8 测试驱动，历史报告的 .NET 10 生产构建为 NOT RUN；
   本轮仅在独立副本用 .NET 10 主机和链接原测试源码的 C# 12 驱动完成 13/13 检查。
   新 CI 必须要求生产目标构建真实执行，不能让 NOT RUN 获得发布通过。
