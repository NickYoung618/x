# 按开发内容调整的测试流（V1.3）

适用范围：框架、S01–S11 各工位 PR、下位机/前端/算法的并行交付及同版本联调。本流程规定**如何选测试、留下什么证据、失败怎样复现与回归**；具体正确行为仍取自 [V1.3 验收映射](architecture/v13-acceptance-map.md)、[工位顺序](station-delivery-order.md)、[全虚拟覆盖计划](fullsim-coverage-plan.md)和该工位的 `test-matrix.md`。未签认的生产 PLC 字段、设备参数、真实配方不能由测试脚本猜出。

## 1. 两个门禁，不能互相冒充

**PR 代码门禁**回答“本次改动有没有破坏已实现的能力”：Linux/Windows CI 基线始终运行，再按受影响模块增加协议、状态机、端口、故障和相邻阶段测试。PR 代码门禁通过可以表示当前实现可评审；若工位依赖尚未交付，PR 保持 Draft，并明确工位验收为 `BLOCKED`。

**工位验收门禁**回答“这一站的业务链是否真实打通”：运行本工位全部适用的正常/拒绝/超时/乱序/恢复行、上一站输入和下一站交接，并用独立进程的设备/相机轨迹核对。S11 还要求发布配方目录、完整整盘、同一候选包的 Windows 桌面。没有独立模拟器、3D 进程、配方或真实设备时，分别记 `BLOCKED` 或 `NOT RUN`，绝不折算成 PASS。旧 V6、V1.3 双/三进程、完整整盘和真机各有独立结果。

状态只用：`PASS`（实际运行且证据完整）、`FAIL`（观察与冻结预期不符）、`BLOCKED`（本层必需依赖未交付）、`NOT RUN`（尚未执行或不属本次门禁）、`N/A`（经规格解释该场景确实不适用）。跳过和零用例不计 PASS；失败重跑保留第一次轨迹，修复后的运行另记 SHA 与 RunId。**计划覆盖率**以适用用例为分母，`BLOCKED/NOT RUN/FAIL` 均不从分母消失。

## 2. 每次开发的固定循环

1. **冻结输入和边界**：记录工位/PR、提交、变更模块、合同版本、合成或正式配方版本、设备/Worker 版本、场景种子；从需求和时序图写出独立预期。每个预期包含终态、动作次数、身份/坐标批次、持久化和允许的下一动作。测试不能调用被测代码计算自己的期望值。
2. **生成影响清单**：运行 `python3 scripts/test_impact.py plan --base main --head HEAD --station S01 --output artifacts/test-impact.json`。可用 `--changed-file` 规划未提交文件，用 `--add-suite` 加上路径推断不出的业务风险。脚本只给**最低范围**；PR 作者复核路径分类，不能删去不方便执行的必测项。未知源码路径进入 `manual_classification`，须补明确归属和测试。
3. **写本工位矩阵**：正常、边界、明确拒绝、已受理后失败、完成反馈丢失/迟到、重复、重启与恢复至少逐一判断适用性；相机/算法/媒体/配方按新增能力扩展。每行写固定输入、故障注入点、精确预期状态和次数、独立证据来源。先冻结，再实现和运行；失败后变更预期须单独注明依据及版本。
4. **本地递进**：静态合同/规则 → .NET 锁定还原、Release 构建与测试 → 真 Host HTTP → 独立 PLC/相机/Worker 进程 → 本工位及相邻站 → 合成整盘。只运行当前已实现层；下一层未执行写 `NOT RUN/BLOCKED`。所有机器同样的固定输入/种子与协议档案。
5. **PR CI 和跨团队复测**：CI 在 Ubuntu 与 Windows 托管 runner 运行已自动化的基线及受影响测试，失败上传 TRX、报文、日志、模拟器轨迹。下位机/前端使用同一提交或校验过的候选包复测各自接口；现场 Windows 使用同一候选包的独立目录。托管 Windows CI 不等于交互桌面/真实设备。
6. **修正与关门**：每次 FAIL 建问题记录，保存首次失败与修复复测；确认原问题消失、下游没有新错误、旧能力仍通过。PR 代码门禁及工位验收分别报告；合并 main 后按同一提交重新跑受影响回归。未决接口决定写入合同，不把合成地址/坐标用于真机动作。

## 3. 改什么，最低加测什么

所有 PR 都保留 `.github/workflows/ci.yml` 的 .NET 10 锁定还原、Release 构建/测试、发布 Host 冒烟、前端检查和旧模拟器框架检查。下表是**追加**范围；每个改变后的控制边界还要做前后站交接和一次恢复/重复验证。

| 改动 | 必须增加的正常与错误检查 | 独立判据 |
| --- | --- | --- |
| PLC 点表、编解码、模拟器、运动适配 | 已知字节/功能码、Float32 字序、写权限、参数锁存、受理≠完成、到位、越界、拒绝、超时、断线、重启、重复/旧反馈；共享模拟器改动另跑旧 V6 | Host 原始 Modbus 与**模拟器自己的**报文/动作次数/物理状态；V1.3 和旧 V6 分表 |
| Workflow、状态机、工位交接 | 当前站矩阵、上一站输出、下一站准入；同盘/件/面/Epoch/Attempt/OperationId；中断与迟到 | 中台状态事件和独立设备轨迹，动作次数不因重试增加 |
| 3D/扫码/相机/采集 | 独立采集进程正常帧、坏帧、无码、错 ID/盘、超时/断线、重复/迟到；坐标单位/标定与来源 | 设备采集记录、帧或固定引用哈希、中台定位/解码结果；相机不能直接给业务槽位冒充 3D 定位 |
| 配方、计划与质量判定 | 唯一匹配/无匹配/歧义、冻结版本、面/相机组合、算法缺失/失败、OK/NG/Pending 和分流 | 原始码、配方版本、任务 DAG、算法输入输出、判定依据；无正式配方仅验合成模板 |
| 算法 Worker 与调度 | 输入完整性、乱序/重复/跨盘、超时/崩溃、旧 Attempt、背压、算法慢时控制通道可用 | 独立 Worker 请求/公开输出、队列/期限、技术终态与质量结果分开 |
| 数据库、媒体、导出 | 意图/文件/数据库/反馈各中断点、满盘/权限、重复初始化、恢复、导出逐项核对 | 已提交记录、媒体文件哈希、独立设备终态、恢复后的查询 |
| Host API、前端、WPF | 权限、重复点击、状态 Revision、断线重连、离线资源、错误展示；受影响页面的浏览器与桌面路径 | HTTP/SignalR 返回、UI trace/截图、后台状态/日志；页面显示“完成”不等于物理完成 |
| CI、测试脚本、打包 | 故意失败、零测试、缺日志/轨迹、错版本、跳过用例必须使门禁拒绝；已发布包从同一 SHA 启动 | CI 退出码、TRX 汇总、包清单与哈希，保留负向门禁运行记录 |

新增故障族先做一次代表路径，再对不同机构、相机组、特殊模板或分流边界补适用组合；安全关键互锁在**所有适用模板**检查。正式配方到位后按[覆盖计划](fullsim-coverage-plan.md)逐个版本做正常整盘，并以故障机制 × 适用边界覆盖异常；不声称枚举无限多的参数/故障组合。

## 4. 联调故障的可复现记录

每个用例的最小证据包：`RunId`、UTC 与单调时间、代码/合同/配方/设备版本、OS/端口/配置（脱敏）、种子、注入脚本、请求与响应原文或十六进制、Host/PLC/相机/Worker 各自日志、最终状态、动作/采集次数、数据库/媒体核对，以及适用时 UI trace。每条事件带 `TrayRunId`、`PartId`、`Face`、`CoordinateEpoch`、`Attempt`、`OperationId`、命令序号/设备会话、阶段和来源；未知字段明确 `null`，不伪造关联。日志既要有稳定错误码和阶段，也要有原始设备状态/报警及异常链，便于判明是谁先失败。

发现失败时按以下顺序处理：

1. 冻结首次失败输入、预期和现场；标出**第一个事实分叉**，不要只贴末轮 HTTP 错误。
2. 分别定位故障**如何产生、哪道准入没有拦住、复核为何没发现、发现后为何没纠正**；检查协议/设备事实、时序与恢复、业务判断、日志绑定、测试盲区。标记未证实的根因假设。
3. 先用原轨迹或固定种子复现；只改变一个怀疑因素做对照。设备响应丢失须核对设备独立执行次数；不能用 Host 日志推断机械没有动作。
4. 修复后跑原用例、相邻站、旧能力和新边界；记录第一次失败、改动 SHA、复测和仍未解释的差异。真实安全故障只在设备方批准的现场规程中测试，软件模拟不能替代硬件保护验证。

问题关闭条件是：原失败有可复现根因或明确未决边界、修复测试通过、关键跨层事实一致、没有新增不受控动作/丢数据；无法证明已执行/未执行的危险动作保持 `Unknown/RecoveryRequired`，不自动重发或把一次连通当恢复完成。

## 5. 机器可读清单的用法和边界

`scripts/test_impact.py` 的 `plan` 从 Git 改动路径生成 `prRequired` 与 `stationAcceptanceRequired`。例如 S01 中改 `simulator/VirtualPlc/` 会同时列 `plc_legacy`、`plc_wire`、`plc_v13`、`recovery` 和工位矩阵；只改工位文档则列 CI 基线和合同评审。`--add-suite` 用于把路径无法识别的业务变化加进来，不能用它删测试。

每个 PR 的 CI 自动上传一个**未指定工位**的 `test-impact-plan` 基础清单；工位负责人还须用 `--station Sxx` 生成本站清单、补工位矩阵并附在 PR。自动上传清单只说明应测范围，不意味着清单项目已经通过。

将实际结果记录为以下结构，`status` 只可写实际状态，`evidence` 指向该 SHA 的本地证据或 CI 运行地址：

```json
{
  "head": "完整提交 SHA，与 plan.head 一致",
  "results": [
    {"id": "core_ci", "status": "PASS", "evidence": "CI run URL 或 artifacts 路径"},
    {"id": "plc_v13", "status": "BLOCKED", "evidence": "接口决定/设备缺口记录路径"}
  ]
}
```

`python3 scripts/test_impact.py check --plan artifacts/test-impact.json --report artifacts/test-results.json --gate pr` 检查 PR 所需项；`--gate station` 再检查工位验收项。任何必需项缺失、跳过、非 PASS、无证据或提交不一致都返回非零。**这个检查只验证清单完整性，不验证所填证据真假**；评审须打开 CI 和独立轨迹核对。`BLOCKED/NOT RUN` 应如实保留在报告，不能为了门禁变绿改为 PASS。新增工位特有用例始终以该站冻结的 `test-matrix.md` 为准，脚本的套件名不能代替逐行断言。

当前可运行入口见[测试总表](testing.md)；S01 精确用例见[首工位矩阵](../specs/005-initial-3d-station/test-matrix.md)。当前独立 3D 与 V1.3 动作联调尚未完成，故这里定义的是持续使用的门禁流程，**不是已经通过的整盘报告**。
